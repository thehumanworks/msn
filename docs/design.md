## Isolation and identity

One SQLite-backed `MsnDurableObject` per `JSON.stringify(['tenant', tenantId])`. This keeps channel creation, indexed messages, idempotency and quotas in one transaction. Different tenants run concurrently on independent objects; a very hot single tenant is bounded by one object's throughput. Preserve the starter's class name and migration v1. SQL schema uses a schema_version table, because DO SQLite does not support PRAGMA user_version; every schema change is an explicit version step in the constructor and each applied version is a row, so the highest row is current. Version 1 is the base schema; version 2 adds the nullable `replyTo`/`correlationId` message columns (ADR 0003), version 3 the `contentType` column (ADR 0004) and version 4 the nullable `bound_username`/`bound_prefix` tenant columns (ADR 0005), each via `ALTER TABLE`, so pre-existing tenants migrate to "unbound" on first load. A fresh database creates the current shape and records the whole history.

Admin-provisioned 256-bit random bearer capabilities grant all-channel read/write within ONE tenant, not deletion. A username is an unverified display identifier **unless the token is bound**: at provision or rotation the administrator may bind the capability to one exact display name or to a name prefix (ADR 0005). A bound token that sends as any other name gets `403 username_bound` before any transaction — nothing is stored, no idempotency key is reserved and no pending poll wakes. Unbound tokens keep the original behaviour: any display name, and members of the same tenant can impersonate each other. Binding therefore stops spoofing only where each human or agent holds its own token; everyone who shares one `MSN_WORKSPACE_TOKEN` shares its bind (or its absence). Rotation keeps the bind by default; the body `{"username": null}` clears it and a new `username`/`usernamePrefix` replaces it, so a routine key rotation never silently widens who a token may send as. `GET /api/tenants/:tenant` tells the holder its bind so the browser can lock the name field; the server check does not rely on the client. No login, cookies, or user directory. Token hashes are SHA-256; comparisons use the runtime timingSafeEqual API. Administrator operations require a separate Worker secret, checked before object dispatch and inside the object. Keys never enter URLs or application logs. Since ADR 0006 the browser stores the key in same-origin `localStorage` only when the person opts to stay signed in; Disconnect or a server-side rejection removes it. Rotation invalidates the old key and wakes/rejects old pending polls. The browser is same-origin, CSP-restricted and renders untrusted content via textContent. It has no admin interface.

## Ordering and polling

Messages have server-generated ISO UTC creation timestamps and tenant-local AUTOINCREMENT integer IDs (never reused). Queries are indexed by channel/deleted/id and return ascending IDs strictly greater than `after`. Cursor advances only to the last delivered message; empty polls retain it. Pages have `hasMore`. Polls are fan-out, NOT a work queue: concurrent listeners all receive a copy; reading never changes history. Repeat any cursor to reread surviving messages. No channel or tenant deletion/recreation endpoint is exposed, avoiding cursor generation ambiguity.

A single synchronous read/register critical section prevents missed notifications. Long polls are bounded to 25 seconds and 128 pending requests per tenant. Timeout, abort, send and key rotation share idempotent timer/listener cleanup. All wakes query SQL again. A client disconnect is not assumed to propagate instantly across Worker→DO fetch; the timer independently guarantees bounded cleanup. Deployments/restarts may fail pending requests: clients reconnect using their last cursor with backoff. UI live history is capped at 1,000 displayed messages, not server retention.

## Writes, deletion and limits

Synchronous transactions atomically check idempotency, create channels, insert messages and update quota counters. Output gates hold responses until persistence. Idempotency keys are channel-scoped; same key+payload returns the existing result, conflicting content returns 409. The payload digest covers username, text and, when any is supplied, `contentType`/`replyTo`/`correlationId`; a plain text/plain send without correlation fields hashes exactly as before either feature, so pre-existing keys still replay. `replyTo` must name an id already stored in the same channel (tombstones included) or the send is rejected with 400 before anything is written; `correlationId` is opaque, ≤128 UTF-8 bytes. Neither field changes fan-out: the server stores and echoes them and never matches, routes or filters on them (ADR 0003). Retries of deleted messages return 410; tombstones retain only metadata/digest, not username/text. Admin deletion immediately removes content from subsequent reads; it cannot recall already-delivered copies (UI Reread refreshes deletion). Cloudflare PITR/backups can retain historical storage for their platform recovery window; this is not a cryptographic erasure guarantee.

Optional payload typing (ADR 0004): `contentType` is `text/plain` (default when omitted) or `application/json`, stored per message and returned on every read. `application/json` is accepted only when `text` parses as JSON; anything else is 400, so readers can `JSON.parse` typed bodies without guessing. The idempotency digest covers `contentType` (a plain `text/plain` send without correlation fields hashes exactly as before, so pre-existing retries still replay). Schema version 3 adds the column with a default; older rows read back as `text/plain`. The browser sends plain text only and renders JSON pretty-printed as text in a `<pre>` via `textContent`. No other MIME types, attachments, binary or multipart bodies.

Application limits: 32 KiB streamed JSON bodies; 16 KiB UTF-8 message text; 128-byte usernames; 64-character tenant/channel slugs; 128-character retry keys; 100 messages/page; 1,000 channels/tenant; 100,000 lifetime messages/tenant; 128 MiB active text+username content/tenant. Deleted rows still count toward lifetime quota to preserve retry tombstones; deletion frees active content quota. IDs stay safely below JavaScript's safe integer ceiling. History does not expire automatically. Quota failures reject writes explicitly; there is no silent retention or data loss. A new tenant is required at the lifetime limit.

Cloudflare docs currently describe 10 GB/object on Paid and 1 GB/object on Free, plus account/plan request and storage quotas. Application content and row limits leave headroom, but billing, index overhead and account quotas still require monitoring. Continuous long polling keeps DOs active and incurs duration/request cost. This is a capability-secured team service, not a public abuse-resistant chat network; per-member identity beyond a bound token, per-channel ACLs, read receipts, global rate limiting, queues and multi-region replication outside Cloudflare DO guarantees are not claimed. Several tokens per tenant (so agents need not share one key) is a recorded follow-up, not implemented.
