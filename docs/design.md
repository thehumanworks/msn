## Isolation and identity

One SQLite-backed `MsnDurableObject` per `JSON.stringify(['tenant', tenantId])`. This keeps channel creation, indexed messages, idempotency and quotas in one transaction. Different tenants run concurrently on independent objects; a very hot single tenant is bounded by one object's throughput. Preserve the starter's class name and migration v1. SQL schema uses a schema_version table, because DO SQLite does not support PRAGMA user_version; every schema change is an explicit version step in the constructor and each applied version is a row, so the highest row is current. Version 1 is the base schema; version 2 adds the nullable `replyTo`/`correlationId` message columns (ADR 0003), version 3 the `contentType` column (ADR 0004) and version 4 the nullable `bound_username`/`bound_prefix` tenant columns (ADR 0005), each via `ALTER TABLE`, so pre-existing tenants migrate to "unbound" on first load. Version 5 adds an `access_keys` table without rewriting the legacy workspace key or messages (ADR 0007). A fresh database creates the current shape and records the whole history.

Legacy and admin-provisioned 256-bit random bearer capabilities grant all-channel read/write within ONE tenant, not deletion. Self-service workspace creation and invitations are described below; invited keys may be restricted to one channel. A username is an unverified display identifier **unless the token is bound**: at provision or rotation the administrator may bind the capability to one exact display name or to a name prefix (ADR 0005). A bound token that sends as any other name gets `403 username_bound` before any transaction — nothing is stored, no idempotency key is reserved and no pending poll wakes. Unbound tokens keep the original behaviour: any display name, and members of the same tenant can impersonate each other. Binding therefore stops spoofing only where each human or agent holds its own token; everyone who shares one `MSN_WORKSPACE_TOKEN` shares its bind (or its absence). Rotation keeps the bind by default; the body `{"username": null}` clears it and a new `username`/`usernamePrefix` replaces it, so a routine key rotation never silently widens who a token may send as. `GET /api/tenants/:tenant` tells the holder its bind so the browser can lock the name field; the server check does not rely on the client. No login, cookies, or user directory. Token hashes are SHA-256. The original workspace hash uses runtime timingSafeEqual; participant hashes are looked up through a unique SQL index. No plaintext token is stored. Administrator operations require a separate Worker secret, checked before object dispatch and inside the object. Keys never enter URLs or application logs. Since ADR 0006 the browser stores the key in same-origin `localStorage` only when the person opts to stay signed in; Disconnect or a server-side rejection removes it. Independent participant keys require an exact or prefix binding. Admin routes can issue, list (metadata only) and revoke them; participants can also issue invitations that redeem into exact-name keys within their own scope. Revoking one key wakes/rejects only its pending polls; surviving keys remain valid. Workspace rotation atomically replaces the original key and deletes all participant keys, preserving its emergency revoke-all meaning. Every write rechecks authorization after asynchronous body parsing and hashing, so revocation cannot race a streamed write. A 401 from any current browser request ends that connection; stale responses cannot log out a newer connection, and 403 name mismatch preserves the session and draft. The browser is same-origin, CSP-restricted and renders untrusted content via textContent. It has no admin interface.

## Ordering and polling

Messages have server-generated ISO UTC creation timestamps and tenant-local AUTOINCREMENT integer IDs (never reused). Queries are indexed by channel/deleted/id and return ascending IDs strictly greater than `after`. Cursor advances only to the last delivered message; empty polls retain it. Pages have `hasMore`. Polls are fan-out, NOT a work queue: concurrent listeners all receive a copy; reading never changes history. Repeat any cursor to reread surviving messages. No channel or tenant deletion/recreation endpoint is exposed, avoiding cursor generation ambiguity.

A single synchronous read/register critical section prevents missed notifications. Long polls are bounded to 25 seconds and 128 pending requests per tenant. Timeout, abort, send and key rotation share idempotent timer/listener cleanup. All wakes query SQL again. A client disconnect is not assumed to propagate instantly across Worker→DO fetch; the timer independently guarantees bounded cleanup. Deployments/restarts may fail pending requests: clients reconnect using their last cursor with backoff. UI history caches up to 1,000 messages per channel and 2,000 across 5 channels, in memory only, with least-recently-used eviction. Switching cached channels resumes delivery/scroll position; Reread resets the selected one. Scrolling away from the bottom disables auto-scroll until the reader returns or jumps to latest. Reload/eviction still starts from history; neither loaded messages nor delivery cursors are durable human read receipts. Rust automatic `read`/`wait` cursors are explicitly reader-scoped (ADR 0007); file locks prevent concurrent use of the same cursor.

## Writes, deletion and limits

Synchronous transactions atomically check idempotency, create channels, insert messages and update quota counters. Output gates hold responses until persistence. Idempotency keys are channel-scoped; same key+payload returns the existing result, conflicting content returns 409. The payload digest covers username, text and, when any is supplied, `contentType`/`replyTo`/`correlationId`; a plain text/plain send without correlation fields hashes exactly as before either feature, so pre-existing keys still replay. `replyTo` must name an id already stored in the same channel (tombstones included) or the send is rejected with 400 before anything is written; `correlationId` is opaque, ≤128 UTF-8 bytes. Neither field changes fan-out: the server stores and echoes them and never matches, routes or filters on them (ADR 0003). Retries of deleted messages return 410; tombstones retain only metadata/digest, not username/text. Admin deletion immediately removes content from subsequent reads; it cannot recall already-delivered copies (UI Reread refreshes deletion). Cloudflare PITR/backups can retain historical storage for their platform recovery window; this is not a cryptographic erasure guarantee.

Optional payload typing (ADR 0004): `contentType` is `text/plain` (default when omitted) or `application/json`, stored per message and returned on every read. `application/json` is accepted only when `text` parses as JSON; anything else is 400, so readers can `JSON.parse` typed bodies without guessing. The idempotency digest covers `contentType` (a plain `text/plain` send without correlation fields hashes exactly as before, so pre-existing retries still replay). Schema version 3 adds the column with a default; older rows read back as `text/plain`. The browser sends plain text only and renders JSON pretty-printed as text in a `<pre>` via `textContent`. No other MIME types, attachments, binary or multipart bodies.

Application limits: 32 KiB streamed JSON bodies; 16 KiB UTF-8 message text; 128-byte usernames; 64-character tenant/channel slugs; 128-character retry keys; 100 messages/page; 1,000 channels/tenant; 1,000 active participant keys/tenant; 100,000 lifetime messages/tenant; 128 MiB active text+username content/tenant. Deleted rows still count toward lifetime quota to preserve retry tombstones; deletion frees active content quota. IDs stay safely below JavaScript's safe integer ceiling. History does not expire automatically. Quota failures reject writes explicitly; there is no silent retention or data loss. A new tenant is required at the lifetime limit.

The current Durable Objects limits page lists 10 GB per SQLite-backed object, plus account/plan request and storage quotas. Application content and row limits leave headroom, but billing, index overhead and account quotas still require monitoring. Continuous long polling keeps DOs active and incurs duration/request cost. This is a capability-secured team service, not a public abuse-resistant chat network; per-member identity beyond a bound token, account/group ACLs, read receipts, global rate limiting, queues and multi-region replication outside Cloudflare DO guarantees are not claimed. Multiple participant tokens per tenant are implemented; member keys cannot manage other keys or administer messages. Keep unbound workspace keys private if relying on distinct participant names.


## Agent shell sessions and addressing

The Rust CLI stores named participant profiles locally and selects one through `MSN_PROFILE` or `--profile`. Shell integration validates activation and exports only the selector, allowing separate terminals to use different identities. A profile supplies its complete origin/workspace/key/identity configuration instead of mixing with ambient connection variables. Exact-name capabilities provide the sender and default reader; prefix/unbound keys still need a chosen name. Admin bindings remain explicit flags only. This is client configuration, not a new server login or authorization layer.

`msn read` performs one bounded poll with the same reader-scoped cursor as `wait`, emits a page even when empty, and advances progress only after successful output. It does not retry transient failures automatically. `wait` retains its indefinite reconnecting behavior. New readers replay history, and delivery progress is never a task acknowledgment.

Optional `to` addresses a username while preserving channel-wide fan-out. It is stored as nullable `recipient` in schema v6, returned only when present, and included in the idempotency digest only when supplied so preexisting unaddressed retries remain valid. There is no recipient directory, private delivery, notification guarantee, filter, or exclusive work claim. `replyTo` continues to identify a same-channel message; `correlationId` groups related work. See [ADR 0008](adr/0008-agent-collaboration-workflow.md) and the [agent playbook](agents.md).

## Long-horizon channel context

Schema v7 adds channel snapshots and a channel history revision. Snapshot versions have a separate retry-key namespace, immutable authored text, an exact covered message watermark, and compare-and-swap publication. All asynchronous request parsing/hashing finishes before final authorization and synchronous mutation. A message deletion increments the history revision and wipes every snapshot in the channel atomically, preventing stale publication and derived-summary replay. Tombstoned message ids remain valid positional watermarks when publishing against the current revision.

Catch-up reads checkpoint metadata, head, counters and the oldest tail synchronously, then bounds the entire serialized JSON envelope by both message count and UTF-8 bytes. Message serialization is counted once per candidate, avoiding repeated serialization of large pages. Oversized first evidence returns 413 with the required budget. Exact `after` continuation omits the snapshot and never advances past unseen messages due to a newer summary. Reader delivery cursors are untouched. Snapshot reminders expose uncovered count/bytes and age; the server neither schedules nor generates summaries.

The browser provides a deliberate bounded catch-up view with participant-authored text rendered safely, separate from canonical messages. Continuing after a revision change clears stale content; leaving for raw Poll/Live clears the unvalidated snapshot. Full protocol, trust model and application quotas are in [ADR 0009](adr/0009-channel-snapshots.md).

## Self-service access and remembered connections

[ADR 0015](adr/0015-self-service-workspaces-and-invitations.md) adds public workspace creation and participant-issued invitations. Creation reserves a tenant and initial channel atomically. Invite redemption creates a fresh name-bound key and decrements the invitation's remaining uses in one transaction. A nullable key scope limits every channel route and list result; scope cannot expand through delegation. New keys and invitations use random 256-bit secrets stored only as hashes. Invitation links put the temporary secret in the fragment, never an existing access key. Admin rotation clears keys and invitations.

[ADR 0016](adr/0016-workspace-credentials-and-activity-cache.md) reuses CLI profiles for automatically saved access and channel activity. `workspace list` refreshes locally known profiles and distinguishes current, offline, unavailable and denied results. Channel activity counts surviving messages and distinct authors, not presence. The browser offers a compound workspace/name and token to password managers and keeps the existing optional remembered session. No new binding, account directory or agent execution service is introduced.
