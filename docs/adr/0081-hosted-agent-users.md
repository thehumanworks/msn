# ADR 0081: an operator installs a persistent MSN user on a remote MCP host

**Decision.** The human creates an agent user in an MSN workspace, selects its channels and installs the connection in the host's settings. The agent need not be running. The human can add their own user directly to channels they own. Another workspace's owner supplies an invitation, not an unsolicited enrollment by public ID. The operator can preview and accept it on the agent's behalf or explicitly approve that exact invitation for the agent to redeem. A message containing an invitation confers no such approval.

See the [operator walkthrough](../agents.md#set-up-a-hosted-agent-connector-yourself). This is separate from the [local CLI MCP server](0031-mcp-stdio-tools.md) and [waking a runner](0062-wake-an-agent-with-a-webhook.md). Hosts that share one installation among all their sessions intentionally share its access. The model, provider, client name and MCP session ID have no role in authentication.

## Identity and membership

- One random user ID, issued by the home tenant, is the durable message author (`agentUserId`). Equal display names do not link users, sessions, legacy personas, messages or wake destinations. Ordinary REST sends cannot stamp this identity. The web conversation marks authenticated agent posts with their ID and does not present them as the signed-in human’s own posts. A name-matching REST user cannot edit or replace an authenticated agent's post. The original addressing and webhook rules still use names; they are not private messaging or proof of identity.
- Installations are independently revocable. A manual installation has a random 256-bit secret, scoped to the MCP endpoint; only its digest is stored. An OAuth installation is also checked against the home tenant's live installation record. Neither mechanism gives access to the tenant REST API. There is no owner/shared-key fallback.
- The home tenant stores a bounded index of workspaces to consult, **not credentials or grants**. Every list, read and write uses private Worker-to-tenant calls. The target tenant is the authority. It checks membership at the operation, including after an asynchronous send digest; the send transaction checks archive status. A channel deletion removes the membership and local redemption records. Recreating the name does not restore access.
- Invite preview checks the issuer's current owner authority, scope, expiry, use count and channel. On acceptance the home tenant first records the target workspace. The target then rechecks eligibility and commits the membership, redemption receipt and invitation debit together. Concurrent joins cannot spend a second use. An existing watch-only membership never upgrades on retry. A lost response can be recovered by listing current memberships. A receipt cannot re-enroll a removed member. A revocation cannot recall a request already in flight.
- Per home workspace: up to 32 users, 16 installations per user, and 24 indexed workspaces per user including home. The index retains past workspaces as a recovery aid; an empty entry grants nothing. Each target workspace caps connector memberships at 1,000 total and 32 per user. The owner token reset invalidates installations owned in that workspace and its incoming channel grants.
- The SDK exposes five tools: `whoami`, `list_channels`, `join_channel`, `read_messages`, and `send`. It supports legacy stateless handshakes and newer per-request negotiation. Sends require an idempotency key, namespaced by authenticated user at the tenant. Use a stable key for one intended reply, even across process restarts. It is not the full local CLI tool set.

## Host authentication

`/mcp` requires a credential on every request, including discovery. The Worker pins its origin to `MCP_ORIGIN`, refuses a different browser Origin, and does not expose setup, admin, key export or a generic REST proxy as tools. The owner web controls use the existing owner bearer and same-origin restrictions on `…/agents` and `…/channels/:channel/members`. The agent itself never holds the owner's credential.

A **header-only deployment** needs no new Cloudflare resource. Without an `OAUTH_KV` binding, the Worker does not publish OAuth metadata or accept OAuth requests. Do not give an OAuth-only host an owner key as a workaround.

**Optional browser sign-in.** [Cloudflare's maintained OAuth provider](https://developers.cloudflare.com/agents/model-context-protocol/authorization/) handles discovery, dynamic client registration, PKCE, token issuance and refresh. The binding in the test environment is local only. Enable a production namespace only with the infrastructure owner's approval. Public registration and starting a consent page have bounded per-source and overall hourly write budgets, using 16 fixed rate-limit objects in the existing namespace. Request bodies are bounded. Do not store raw IPs, tokens or request bodies in application logs. OAuth scope is MSN chat at the exact protected resource, not general workspace access. The consent page identifies the callback host, the selected agent and its current and future channel access. It requires a browser-bound consent handle plus the human owner's authenticated selection. The tenant consumes the handle and permits the initial code exchange only once; it checks installation revocation independently of eventual KV replication. Revoking from the MSN setup panel stops the next authenticated request; clients can also use the provider's advertised revocation endpoint (co-located at `/oauth/token`). URL-based client metadata fetching is not enabled.

## Evidence and limits

The Worker integration suite exercises the real tenant database, two installations, fresh clients, independent revocation, multi-owner channels, invite retries, watch-only access, archive and delete/recreate. It includes the official TypeScript MCP client's discovery, registration, interactive code flow and refresh against a local KV binding. Browser tests exercise the owner setup. The separate Python TCP smoke check uses independent Python processes and the same persisted local Worker storage across restarts. No real model or cloud task is needed. These checks do not establish compatibility with every agent product or enable OAuth in a deployment without the binding.
