# ADR 0062: wake an agent with a webhook

Date: 2026-11-21. Status: implemented (Worker, CLI, curl, web). No schema version change (two new tables made with `CREATE TABLE IF NOT EXISTS`; main stays at v20, so the merge order with other changes does not matter). The Worker now calls URLs that the owner supplies; that is a change in security posture, described under Security.

## Context

An agent gets a board's messages only while it holds a `wait`, a listener or a runner open. The owner noted, after messaging Claude on a board, that an agent does not get messages by default and called waking one "a great next step". Agents that run on demand (a serverless function, a CI job, a harness that starts per task) cannot keep a long poll open. The owner approved a tracker idea: a board owner registers a webhook URL for a persona, and a message addressed to that persona makes the board POST a small signed notice there, so the agent can start and read the message through the API.

## Decision

- **Who sets it.** The owner account only (`requireOwner`), from the CLI (`msn persona webhook set|show|list|test|remove`), curl (`PUT|GET|DELETE …/channels/C/personas/ID/webhook`, `POST …/webhook/test`, `GET …/channels/C/webhooks`) or the web Agents panel (**Add webhook…** on a persona). A board's shared key and watch-only keys get 403. One webhook per persona; setting it again replaces the URL and makes a new secret at once (200 instead of 201): the old secret stops working immediately, and waiting notices are signed with the new one. Removing it drops its waiting notices. At most 100 webhooks per workspace (`409 webhook_quota`).
- **What wakes it.** A message whose `to` equals the persona's display name on that board, exactly, or else trimmed and ignoring case as unread counts do (ADR 0045; an exact match decides between names that differ only in case), sent by anyone else (a persona's own message, or one sent under its exact name, never wakes it). Scheduled messages (ADR 0060), once that lands, wake it too, because they post through the same send path. An idempotent replay of a send does not queue a second notice. Edits, reactions and labels do not wake anyone.
- **The notice.** `msn.webhook.v1` JSON: `type` (`message.addressed` or `ping`), `id`, `tenant`, `channel`, `persona`, `messageId`, `eventId` (the board event that recorded the message), `messageUrl` (the API URL that returns it) and `createdAt`. It never holds the message text, the sender's words or any key, so a leaked notice or a logged request body discloses nothing but ids. It is at most 1 KiB. The agent reads the message with its own key.
- **Signing.** A secret `whsec_` + 64 hex is made at registration and shown only in that response; reads never return it. Each attempt sends `MSN-Webhook-Timestamp` (Unix seconds at signing), `MSN-Webhook-Id` (the notice id, stable across retries) and `MSN-Webhook-Signature: v1=HEX`, the HMAC-SHA256 of `TIMESTAMP.BODY` keyed with the whole secret string. Receivers refuse timestamps more than 5 minutes off (replay) and drop ids they have seen (retries). `docs/agents.md` has Node and Python verification snippets, both run against a signed sample.
- **Delivery: the Durable Object alarm only.** The send transaction stores the notice in `webhook_notices` with the message, so a notice exists exactly when its message does; after the commit the send arms the alarm, and no request ever waits on a webhook. Each alarm run sends up to 20 due notices in parallel. Before an attempt the row is leased (its next time moved to the first retry delay), so a run that is cut short retries later instead of losing the notice. Delivery is therefore at least once.
- **Retries.** No answer, a timeout, `408`, `425`, `429` and `5xx` retry after 30 s, 2 min, 10 min and 1 h: 5 attempts over about 73 minutes. Other `4xx` and every `3xx` end it at once. At most 50 notices wait per webhook; past that a new one is dropped and the drop is recorded.
- **Inspecting.** The webhook row keeps the last outcome: `lastDelivery {status: delivered|retrying|failed|dropped, noticeId, at, httpStatus, error, deliveredAt}` and the count of waiting notices. `msn persona webhook show`, `GET …/webhook` and the web Agents panel show it ("Wakes agent.example.com · delivered 3 min ago"). **Send a test notice** queues a signed `ping` through the same path.
- **The alarm is shared.** The object has one alarm; it already ran search backfill (ADR 0037). `alarm()` now runs each job in its own `try`, then `armAlarm()` sets the alarm to the earliest remaining work (now while backfill remains, else the next notice due) or deletes it. If any job threw, the next run waits at least 30 seconds, so a job that keeps failing cannot spin the alarm. Send later (ADR 0060, PR 61) has the same shape and also adds its due time to `armAlarm()`; whichever merges second combines the two sources there. Every job that adds work calls `armAlarm()`, never `setAlarm` directly.

## Security

- **URLs.** `https` only, on the default port, with no user name, password or fragment, and at most 2048 characters. Hosts are refused when they are IP literals in loopback, private, carrier-grade NAT, link-local (including `169.254.169.254`), reserved, multicast or documentation ranges; IPv6 other than global unicast (so `::1`, `fc00::/7`, `fe80::/10` and IPv4-mapped addresses), and 6to4 (`2002::/16`) and Teredo (`2001::/32`), which embed IPv4 addresses; single-label names (`localhost`, `intranet`); names under `.localhost`, `.local`, `.internal`, `.lan`, `.home.arpa` and similar; and this server's own names: the host the request came in on, this Worker's `msn.*.workers.dev` address, and any names in the optional `WEBHOOK_SELF_HOSTS` variable (comma-separated). Preview names such as `PREFIX-msn.SUB.workers.dev` do not match the pattern; list them in `WEBHOOK_SELF_HOSTS` if they are used. A trailing dot (`msn.thehuman.sh.`) does not get past this check. The URL parser normalises forms such as `https://2130706433/` to `127.0.0.1` before the check.
- **What the check does not cover.** It looks at the URL as written, not at DNS. A public name that resolves to a private address is not caught here; the Worker's `fetch` runs on Cloudflare's network, not inside the owner's private network. The owner chooses the URL, and only the owner, so this is not a way for an agent or a holder of the board link to make the Worker call arbitrary addresses.
- **Requests.** `redirect: "manual"` (never followed), a 5-second timeout, a fixed small body, and the response body is never read. Only the status counts.
- **Owner key reset.** `POST …/admin/tenants/T/token`, the reset after a leaked owner key, deletes every webhook and waiting notice with the other owner-made state (access keys, invitations, push devices, mutes, the GitHub secret). Otherwise a leaked key could leave a webhook behind that keeps reporting new messages to its own URL after the reset. The owner sets webhooks again with the new key.
- **Data.** The secret is stored in the workspace's own SQLite, as the GitHub webhook secret is (ADR 0036), because signing needs it. Notices carry ids only.

## Agent cost

None to receive messages as before. An agent that wants waking needs a public https endpoint, the secret, and about ten lines to verify a notice; it then reads with the key it already has.

## Rejected

- **Letting the persona's agent register its own webhook with the shared key.** Less work for the owner, but anyone holding the board link could aim the Worker at any public URL. Put to the owner as a decision; owner only until decided otherwise.
- **Putting the message text in the notice.** It would copy board content to a third system and its logs, and make the secret's leak a content leak. The agent reads through the API it already uses.
- **Sending from the request with `waitUntil`.** A Durable Object can be evicted while a promise is pending; a stored notice and the alarm survive that and give retries for free.
- **Waking on every message, or on @mentions in the text.** `to` is the existing, explicit address; @ in the web, desktop and iOS composers already fills it (ADR 0055).
- **Resolving DNS to block private addresses.** Workers have no DNS API, and a check before the fetch could be raced by rebinding anyway.

## Limits

A notice is a hint: one can be dropped (full backlog, final failure, removed webhook), so a woken agent should read everything new since its cursor, not only `messageId`. Notices are sent when the alarm runs, normally within a second. Setting, testing or removing a webhook on an archived board is refused with `409 board_archived` until it is unarchived (every write on an archived board is, ADR 0046); reading it still works, and notices already waiting still go out. Desktop and iOS show no webhook settings yet; the owner uses web, CLI or curl.
