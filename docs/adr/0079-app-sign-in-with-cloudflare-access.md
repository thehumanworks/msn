# ADR 0079: sign in to the iOS app with Cloudflare Access

Date: 2026-11-22. Status: revised after security review, not yet deployed. The first version returned the code on a custom URL scheme, which let another app collect it (see Revision). Adds one route option, an https callback page, an `apple-app-site-association` file, one endpoint and one Durable Object table; no change to the Access application.

## Context

The owner asked for Cloudflare Access sign-in in the iOS app. The web app signs in by opening `/login`, which only an Access application covers. The Worker verifies the `Cf-Access-Jwt-Assertion` (signature against the team's JWKS, issuer, audience, expiry), opens an owner connection for the account derived from issuer and subject, and redirects to `/#account=CONNECTION`. That puts the account key in a URL, which a native app cannot receive and which the apps must never do. The CLI instead exchanges an Access token from `cloudflared` at `POST /api/account/login`, which a phone cannot run.

Options considered:

- **Embedded web view** watching for `/#account=`. No server change, but Google and other identity providers refuse embedded browsers, and the key still travels in a URL.
- **One-time code with a verifier on a custom scheme** (`msn://login`), as in OAuth's PKCE (RFC 7636) for native apps (RFC 8252). The first version. Unsafe on its own: see Revision.
- **One-time code with a verifier on an https callback** that iOS delivers only to an app the server names (`ASWebAuthenticationSession`'s `.https(host:path:)` callback, iOS 17.4 and later). Chosen.
- **A consent page** ("Sign in to the MSN iPhone app as X?") behind a same-origin POST, keeping the custom scheme. It makes the hand-off visible but still pays out to whichever app started the sign-in if the person taps Continue.

## Decision

- **The app opens `/login?app=CHALLENGE` in the system sign-in sheet** (`expo-web-browser`'s `openAuthSessionAsync` with `preferUniversalLinks`, which is `ASWebAuthenticationSession`), so the person's Safari session, passkeys and identity provider work as on the web. `CHALLENGE` is the lowercase hex SHA-256 of a 32-byte random verifier that never leaves the app until the exchange.
- **The Worker answers with a code, not a key, on an https callback.** After verifying Access exactly as for the web sign-in, `/login?app=` stores a single-use code in the account's Durable Object (`app_logins`: code hash, challenge, email, expiry) and answers `303 https://HOST/app/signed-in#account=ACCOUNT&code=CODE` on its own origin. The answer rides in the fragment, which browsers never send, so the code stays out of request logs. A malformed challenge is a 400. Codes live two minutes, at most 20 may wait per account, and expired rows are deleted whenever a code is stored or spent.
- **Only the associated app receives the callback.** The Worker serves `/.well-known/apple-app-site-association` with `{"webcredentials": {"apps": [...]}}` from the `APPLE_APP_IDS` setting (`TEAMID.bundle-id`, comma-separated; the file is a 404 when it is empty). The app carries the `webcredentials:msn.thehuman.sh` Associated Domains entitlement. iOS checks both before it starts a sheet with an https callback, so another app cannot start one that completes on `/app/signed-in`. Outside the sheet, `/app/signed-in` is a plain page that echoes nothing and tells the person to sign in again from the app. The app's own URL scheme is its bundle id (`sh.thehuman.msn.next`), which Expo's linking needs; nothing is ever sent to it.
- **`POST /api/account/app-login` trades `{account, code, verifier}` for the owner connection** the web sign-in opens (`{url, tenant, username, token, owner}`). The code is spent on the first attempt, right or wrong, including a malformed verifier, and the verifier's hash must match the stored challenge. Cross-origin browser callers are refused, as for `/api/account/login`.
- **Refusals cross Durable Object RPC as values.** An `HttpError` thrown in the object reaches the Worker as a plain error and would answer 500, so the two new RPC methods return `{refused: {status, code, message}}`, which the Worker turns back into the HTTP error.
- **`/login` on another hostname keeps the challenge.** The redirect to `ACCESS_LOGIN_URL` forwards a well-formed `app` parameter and still drops everything else.
- **The app checks what comes back.** It offers the button only for a server on its associated hosts (`msn.thehuman.sh`) whose `/api/account/config` reports `cloudflareAccess: true` and a sign-in page on the same origin. It accepts only its own server's `/app/signed-in` with a well-formed account and code, posts only to that origin, and refuses a connection for another origin or account. The key then goes through the shared `signInWithKey`, which checks it and saves it to the keychain.

## Revision

A security review of the first version found that the verifier does not protect a sign-in someone else starts: whoever picks the challenge holds its verifier. With the code on `msn://login`, any app on the phone could open the sign-in sheet with its own challenge and `msn` as the callback scheme; the sheet shares Safari's Access session, so the Worker issued a code without asking and that app exchanged it for an owner key. A web page could equally send Safari to `/login?app=…` and let whichever app claims `msn://` receive the code. Custom schemes are not owned on iOS, so the fix moves the callback to an https URL that iOS delivers only to the associated app.

## Consequences

- Another app cannot start a sign-in that completes, because iOS refuses its https callback on a host it is not associated with, and the server never sends the code to a custom scheme. A page that sends the owner's Safari to `/login?app=…` lands the code on `/app/signed-in` in the owner's own browser tab, which the page cannot read. A code copied out of the app's own sign-in is useless without its verifier.
- Cloudflare sign-in works only with the servers in the app's entitlement, and only after the Worker serving the association file is deployed and Apple's CDN has fetched it. A self-hosted server needs its own build of the app. It cannot be exercised against a local Worker.
- Each app sign-in creates an owner key, like each web or CLI sign-in. Signing out of the app does not revoke it; there is no key revocation endpoint yet.
- The Access application needs no change: Access ignores query strings when matching application paths, and its sign-in redirect keeps them (checked on msn.thehuman.sh: an unauthenticated `/login?app=…` goes to the team sign-in page with `redirect_url=/login?app=…`). `/.well-known/apple-app-site-association` and `/app/signed-in` sit outside the Access application and answer without a redirect.
- Tested with Worker tests (a signed-in owner's `/login?app=` returning the code on the https callback and the full exchange, single use including three exchanges at once, wrong and malformed verifiers, expiry, quota, malformed input, the association file and the callback page, the redirect hop, and `/login?app=` without or with a forged assertion) and app tests against a fake server and sign-in sheet. A real sign-in can only be checked after deploying, on a device signed in to the team.
