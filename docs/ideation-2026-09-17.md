# MSN collaboration ideas — 17 September 2026

The strongest direction is a **recoverable project workspace**: agents can see the goal, current work, dependencies, decisions, and evidence without reconstructing them from a long conversation. Keep readable messages as the shared record, and add a few coherent views and recovery operations around them.

This is an ideation report, not an implementation release. The exercise used **12 Grok agents and 3 Sol agents**, all proposing, challenging peers, and voting in MSN's `swarm / ideation` channel. No Astra agents participated in this round.

## What actual use changed

**The swarm produced real peer exchanges.** Before the final coordinator wrap-up, the transcript contained 149 messages from 16 authors: 15 subagents and the coordinator. Every subagent replied to another subagent; there were 44 such addressed reply edges. All 15 submitted a ballot. These are structural participation counts, not measures of response quality. No Tomas-authored message appeared during the voting window.

**A snapshot was useful but insufficient.** Checkpoint v1 covered 125 messages containing 137,060 UTF-8 bytes of message text and used 7,370 bytes of authored text. It enabled a compact candidate slate for the next round. This is lossy summarization, not a measured token-saving or recovery-quality benchmark: resumed agent sessions retained their earlier context. The first checkpoint was not published until the end of the proposal round despite existing snapshot reminders. That supports trying explicit ownership and scheduled requests before adding an automatic summarizer.

**An incorrect technical premise spread and survived a correction.** Several agents said safe exact-ID lookup required a new Worker endpoint. In fact, a helper can poll after `N-1` and reject any returned row whose ID is not `N`; it cannot distinguish a deleted row from an absent one. The coordinator corrected this in message [364](examples/ideation-2026-09-17/transcript.md#message-364) and checkpoint v1, but eight ballots still used the mistaken premise.

A concrete [probe](examples/ideation-2026-09-17/point-lookup-demo.json) requested `ideation #240`, received `#241`, and rejected it; requesting `#241` accepted it. A targeted [correction audit](examples/ideation-2026-09-17/transcript.md#message-381) then caused all eight agents to amend their rankings. Evidence lookup fell from 59 to 41 ballot points. This is evidence for a correction-propagation problem, not proof that a particular new message schema solves it.

**Critique changed other proposals materially.** The separate `doctor` command became one useful `start` operation. Exclusive ownership became a deferred experiment behind task visibility. Dual delivered/processed watermarks became one explicit processing cursor. Artifact receipts stopped rejecting all dirty files and instead represented their provenance honestly. Attention proposals stopped claiming selective compression could guarantee recall of arbitrary unmarked decisions.

The final ranking puts recurring task reconstruction above one-time entry friction, raises recovery and checkpoint correctness, and lowers evidence lookup because a safe workaround exists. The raw totals and original/amended ballots remain available for readers who prefer a different weighting.

The Sol skeptic's main dissent is worth preserving: task state could turn MSN into a weak issue tracker with stale ceremony, while disciplined prose and snapshots may suffice. Test a small typed-event convention before expanding the server. The same caution applies to dissent tracking and structured decisions: use one shared event/projection design, not a proliferation of mini-products.

Ballots were public and agents shared a debate; these are correlated judgments, not blind independent samples. Twelve Grok votes and three Sol votes are not a balanced model comparison. Every Cursor launch requested `cursor-grok-4.6-high-fast`; G07's first initialization reported `Cursor Grok 4.6 Fast`, while its second reported `Cursor Grok 4.6 High Fast`. The manifest preserves this discrepancy. Native Sol agents used medium reasoning. No new app code, deployment, or product benchmark was performed.

## Recommended sequence and experiments

1. **Build a dependable entry and work loop:** `start`, `peek/commit`, and one evidence lookup interface. Verify that entry leaves cursor state untouched, continuation remains bounded, and a crash before commit replays the work.
2. **Trial the shared project view:** use a single event vocabulary for assignment, blockers, readiness, integration, and conflict. Ask a returning agent and coordinator to identify all current work from the view; compare against disciplined prose before expanding the product.
3. **Make recovery preserve consequential changes:** assign a checkpoint steward, record explicit corrections and unresolved objections, and test a returning agent against a seeded stale premise. Citation presence must never become a semantic “verified” badge.
4. **Reduce context only with a decision-recovery check:** compare indexed and full views on the same workload, including peer-addressed decisions. Explicitly test the unmarked-decision limitation rather than reporting only fewer bytes.
5. **Run the larger bet:** use 8–15 agents in a dependency chain with targeted subscriptions. Measure useful versus unrelated wakeups and recovery after disconnection. Keep server transport optimization separate from model-visible context savings.

The ambitious destination combines shared work state, durable recovery, and event-driven resumption. It does not require an autonomous scheduler or an LLM-generated “truth” summary as the first step.
